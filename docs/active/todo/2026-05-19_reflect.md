So we have some tooling in ploke-eval through the cli with the commands for protocol and some of
the other commands, I forget which, that use the llm-adjudicated protocols to derive a bunch of
tables and stats about the evals. However, we're moving away from using these and towards
implementing more observability and introspection of tool calls in the ploke-egui front-end. I
would like you to act as orchestrator with the $light-thread-orchestrator and $orchestrator-
conveyor to survey those commands, how to represent them in the UI while keeping allocations and
per-frame allocations and recalculations down so the app stays performant. Consider how we can
represent the output as bar charts, line graphs, and use other high quality data analysis
representation to view a breakdown of the tools in the UI.

The goal of using the front-end is to provide introspection into the loop described in crates/
ploke-eval/src/cli/prototype1_state/mod.rs, in part through the protocols as described in docs/
workflow/evalnomicon/drafts/formal/procedure-notation.md, and to implement a system similar to
the one described in the research paper in .agents/hyper-agents.txt using our tui framework as
described in README.md

At our current stage, we are focused on how to prove that the loop does in fact improve the
results on the target benchmark, beginning with multi-swe-bench. At our current stage of
development, we have tested that the basic first attempt described in docs/workflow/evalnomicon/
drafts/runtime/loop.md has produced and performed the handoff for a successor correctly over 30
generations, and then changed to use the edit surface model as described in docs/workflow/
evalnomicon/drafts/edit-surface/model.md, and have not yet put all of our data together into
something that presents a clear supporting argument for our hypothesis that our framework does
in fact improve the performance of our framework over multiple generations.

Having shown that the core `Crown` mechanics and handoff to the successor runtime is stable, we
moved on to the edit surface modeling and using the actual ploke-tui framework instead of the
minimal include_str example mentioned in the older docs. Since then we have run into many issues
with regard to our tools, and the interaction between ploke-eval and ploke-tui. Our tools are
still known to produce issues like search thrash but we have hopefully been able to handle most
of the issues that would invalidate the run by making it impossible for the models to apply
edits or have a reasonable chance of success.

That is when we put together the ploke-egui crate, because we are hoping to use it both as an
internal dev tool while we refine our multi-generation looping approach for a single-ruler case,
and then to compile it to webassembly and display it on our website, allowing potential design
partners and investors to view the loops as a kind of evidence-based argument that our
application works as described.

One of our primary difficulties in supplying this proof is that doing a fully complete and
comprehensive treatment of the ploke-eval loop would involve using 200+ instances of the multi-
swe-bench we have setup in our project, but doing so would be both inefficient and expensive,
since in the ideal case we would be able to run all instances on all evaluated parent and child
artifacts produced through the loop. However, it would cost over 40 dollars even on the cheaper
open source models, and likely at least 10x that amount for a leading foundation model, for each
node evaluated. Therefore, we have been testing our approach with one instance so far, and using
the self-evaluation of the parent and chld nodes as our primary signal of improvement. Later, we
hope to implement some kind of way to trigger additional instances to be run when there is a
higher likelihood of demonstrating progress in the loop or via periodic checks or similar, to
provide more robust proof.

After the tool calling issues were mostly addressed, we hoped to use the demonstration in ploke-
egui to help with debugging further instances by expanding the introspection and drilldown
features of the front-end to identify when and how our framework mechanisms might still have
issues that we have not been able to detect so far. With regard to the sub-optimal helpfullness
of the remaining tools we may work on some of them to set a good pattern, such as progressive
disclosure on the code graph node discovery tools or making them more recoverable, but part of
our curiousity on how this experiment will develop is around whether or not the multi-generation
loop will be able to implement new or different tools that we would not have anticipated.
Therefore, we want to make sure the pmetrics, selection mechanism, and llm-adjudicated metrics
are working correctly and capable of providing high-signal information to the models, which is
why we are focused on this task implement more observability and introspection of tool calls,
especially regarding metrics and protocols but also more generally, in ploke-egui. it serves
multiple goals we have by helping us debug, determine what other metrics we might need to track
to help the model and how to present the information to the model, how we can present an
intuitive and inspectable interface on our website to provide transparency to potential design
partners and investors, and allow us to evaluate the efficacy of our approach and refine it as
we move into more and more expensive testing.
