- status: alive, unfixed

## Summary

Prototype 1 child self-validation can export Multi-SWE-bench `fix_patch`
evidence that is not cleanly attributable to the candidate being evaluated.

The submitted MBE patch is generated by running `git diff` in
`PreparedSingleRun.repo_root`. For MBE runs that repo root is derived from the
shared benchmark repo cache, for example:

```text
/home/brasides/.ploke-eval/repos/BurntSushi/ripgrep
```

That path is distinct from each candidate node's isolated Prototype 1
`workspace_root`.

The result is that the oracle artifact can describe the state of a shared
benchmark checkout rather than a candidate-owned instance target state. This
can produce repeated, partial, stale, or otherwise misattributed instance
patches.

## Impact

MBE results from affected runs are unsafe to use as candidate-quality oracle
evidence.

Affected symptoms include:

- identical `fix_patch` bytes across distinct candidate nodes
- non-empty MBE patches when `PatchArtifact.applied = false`
- non-empty MBE patches with no applied proposal status entries
- patch paths and apply errors pointing at the shared benchmark checkout
- compile failures that may reflect patch provenance failure rather than model
  capability

## Code Path

The MBE submission writer is in `crates/ploke-eval/src/runner.rs`.

The patch is built through:

```text
write_msb_submission_artifact
  -> maybe_build_msb_submission_record
  -> collect_submission_fix_patch
  -> git_stdout(&prepared.repo_root, ...)
```

The relevant ranges are:

- `crates/ploke-eval/src/runner.rs:1016-1068`
- `crates/ploke-eval/src/runner.rs:3672-3680`

`collect_submission_fix_patch` runs:

```text
git diff --no-ext-diff --binary <base_sha> --
```

with cwd bound to `prepared.repo_root`.

The MBE preparation path derives that repo root from the shared repo cache:

- `crates/ploke-eval/src/msb.rs:130-150`
- `crates/ploke-eval/src/spec.rs:98-120`
- `crates/ploke-eval/src/spec.rs:476-514`

## What Is Proven

- `fix_patch` bytes are generated from `prepared.repo_root`, not from a typed
  proposal artifact.
- For the repeated-hash sample, `prepared.repo_root` resolves to the shared
  benchmark checkout path.
- The sampled candidates have distinct Prototype 1 `workspace_root` paths.
- The repeated patch bytes are identical across multiple nodes.
- Non-empty patches can coexist with failed or absent applied-proposal evidence.

## What Is Not Yet Proven

- The records do not by themselves prove that two child runs mutated the same
  checkout at exactly the same instant.
- Repeated patch hashes can theoretically arise from independent rediscovery of
  the same edit.
- Existing records do not expose a per-run checkout ownership, lock, or lease
  artifact for the benchmark repo path.

## Suspected Failure

The failure is a provenance boundary error:

```text
candidate self-validation evidence
  is packaged from
shared benchmark checkout diff
  instead of
candidate-owned instance target state
```

This makes the exported MBE instance patch a weak projection of the mutable
checkout state, not a reliable artifact of the candidate's own applied edits.

## Fix Direction

1. Give each child self-validation run an isolated instance target checkout or
   worktree.
2. Persist the exact checkout identity used for `git diff`, including the cwd,
   base SHA, and ownership/run id.
3. Treat non-empty `fix_patch` output as invalid oracle evidence unless the same
   run's patch artifact proves applied proposal state and expected file changes.
4. Add a regression test for sibling child self-validations targeting the same
   MBE instance.

## Verification After Fix

A fixed run should show:

- each candidate has a unique instance target checkout path, or a durable
  serialized lease over a shared path
- `fix_patch` cwd is persisted and tied to the run id
- failed, pending, absent, or partial proposal state cannot produce usable MBE
  oracle evidence
- repeated `fix_patch` hashes across sibling candidates are explainable by
  identical applied proposal evidence, not shared mutable checkout state
