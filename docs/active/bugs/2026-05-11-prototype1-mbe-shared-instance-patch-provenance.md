- evidence directory: `docs/active/agents/2026-05-11_mbe-instance-patch-provenance/`
- plan: `docs/active/agents/2026-05-11_mbe-oracle-calibration-plan.md`
- live validation blocked by:

## Summary

Prototype 1 child self-validation can export Multi-SWE-bench `fix_patch`
evidence that is not cleanly attributable to the candidate being evaluated.

Patch commit `c2d0f1eb` adds child-owned MBE instance targets and typed patch
projection checks, but the isolated-target behavior is not live-validated yet.
The first validation run, `p1-mbe-provenance-4g3c-20260511-1`, failed earlier
in the child lifecycle because the broad edit-surface generator selected
archive Markdown files and child artifact persistence failed before self-eval.

On 2026-05-22, the source checkout added a packaging guard for item 3 under
Fix Direction: non-empty MBE `fix_patch` output now requires same-run
`PatchArtifact` evidence showing an applied proposal, a non-empty expected
benchmark-file evidence list, and at least one expected benchmark file change.
This does not by itself prove child-owned target isolation.

The submitted MBE patch is generated by running `git diff` in
`PreparedSingleRun.repo_root`. For MBE runs that repo root is derived from the
shared benchmark repo cache, for example:

```text
/home/brasides/.ploke-eval/repos/BurntSushi/ripgrep
```

That path is distinct from each candidate node's isolated Prototype 1
`workspace_root`.

The result is that the oracle artifact can describe the state of a shared
benchmark checkout rather than a candidate-owned instance target state. This
can produce repeated, partial, stale, or otherwise misattributed instance
patches.

## Impact

MBE results from affected runs are unsafe to use as candidate-quality oracle
evidence.

Affected symptoms include:

- identical `fix_patch` bytes across distinct candidate nodes
- non-empty MBE patches when `PatchArtifact.applied = false`
- non-empty MBE patches with no applied proposal status entries
- patch paths and apply errors pointing at the shared benchmark checkout
- compile failures that may reflect patch provenance failure rather than model
  capability

## Code Path

The MBE submission writer is in `crates/ploke-eval/src/runner.rs`.

The patch is built through:

```text
write_msb_submission_artifact
  -> maybe_build_msb_submission_record
  -> collect_submission_fix_patch
  -> git_stdout(&prepared.repo_root, ...)
```

The relevant ranges are:

- `crates/ploke-eval/src/runner.rs::write_msb_submission_artifact`
- `crates/ploke-eval/src/runner.rs::ensure_msb_submission_patch_evidence`
- `crates/ploke-eval/src/runner.rs::collect_submission_fix_patch`

`collect_submission_fix_patch` runs:

```text
git diff --no-ext-diff --binary <base_sha> --
```

with cwd bound to `prepared.repo_root`.

The MBE preparation path derives that repo root from the shared repo cache:

- `crates/ploke-eval/src/msb.rs:130-150`
- `crates/ploke-eval/src/spec.rs:98-120`
- `crates/ploke-eval/src/spec.rs:476-514`

## What Is Proven

- `fix_patch` bytes are generated from `prepared.repo_root`, not from a typed
  proposal artifact.
- For the repeated-hash sample, `prepared.repo_root` resolves to the shared
  benchmark checkout path.
- The sampled candidates have distinct Prototype 1 `workspace_root` paths.
- The repeated patch bytes are identical across multiple nodes.
- Non-empty patches can coexist with failed or absent applied-proposal evidence.

## What Is Not Yet Proven

- The records do not by themselves prove that two child runs mutated the same
  checkout at exactly the same instant.
- Repeated patch hashes can theoretically arise from independent rediscovery of
  the same edit.
- Existing records do not expose a per-run checkout ownership, lock, or lease
  artifact for the benchmark repo path.

## Suspected Failure

The failure is a provenance boundary error:

```text
candidate self-validation evidence
  is packaged from
shared benchmark checkout diff
  instead of
candidate-owned instance target state
```

This makes the exported MBE instance patch a weak projection of the mutable
checkout state, not a reliable artifact of the candidate's own applied edits.

## Fix Direction

1. Give each child self-validation run an isolated instance target checkout or
   worktree.
2. Persist the exact checkout identity used for `git diff`, including the cwd,
   base SHA, and ownership/run id.
3. Treat non-empty `fix_patch` output as invalid oracle evidence unless the same
   run's patch artifact proves applied proposal state and expected file changes.
   Source-checkout mitigation added 2026-05-22; live campaign retest pending.
4. Add a regression test for sibling child self-validations targeting the same
   MBE instance.

## Verified Mitigation: 2026-05-22

Implemented in `crates/ploke-eval/src/runner.rs`:

- `RunMsbAgentSingleRequest` now preserves the same turn's `PatchArtifact`
  before moving the turn artifact into the run record.
- `write_msb_submission_artifact` receives that same-run patch evidence.
- `ensure_msb_submission_patch_evidence` rejects non-empty MBE `fix_patch`
  output when no same-run patch artifact exists, when no proposal was applied,
  when expected benchmark-file evidence is absent, or when none of the expected
  benchmark files changed.
- The guard runs before `multi-swe-bench-submission.jsonl` or
  `benchmark-patch-projection.json` is written.

Focused tests:

```text
cargo test -p ploke-eval msb_submission -- --nocapture
```

Result on 2026-05-22: passed 6 tests, including regressions for non-empty
submission rejection without applied evidence and without expected-file change
evidence.

Result on 2026-05-22: passed 8 tests, adding coverage that non-empty

## Isolation Hardening: 2026-05-22

Read-only survey found that the Prototype 1 child-eval path already creates a
child-owned instance target cache under:

```text
<node_dir>/instance-targets/<treatment_campaign_id>
```

and passes it to `advance_eval_closure` as `repo_cache_override`. The generic
MBE CLI path still defaults to the shared repo cache, which remains acceptable
outside Prototype 1 as long as the artifact records say so.

Source-checkout hardening added on 2026-05-22:

- `advance_eval_closure` now fails closed when `repo_cache_override` is present
  and any prepared MBE run's canonical `repo_root` is outside that override.
  Both the override root and each prepared run root are canonicalized before
  comparison, so `..`-spelled escapes are rejected.
- Starting DB cache metadata and keys now include `PreparedSingleRun.repo_root`
  and use cache version 2, preventing a path-sensitive indexed DB snapshot from
  one checkout root from being reused for another checkout root.

Focused tests:

```text
RUSTFLAGS=-Awarnings cargo test -q -p ploke-eval eval_closure_repo_cache_override -- --nocapture
RUSTFLAGS=-Awarnings cargo test -q -p ploke-eval starting_db_cache_miss_when_repo_root_changes -- --nocapture
RUSTFLAGS=-Awarnings cargo test -q -p ploke-eval starting_db_cache_miss_when_metadata_changes -- --nocapture
```

Result on 2026-05-22: passed 3 eval-closure override tests and 2 starting-DB
cache identity tests.

## Verification After Fix

A fixed run should show:

- each candidate has a unique instance target checkout path, or a durable
  serialized lease over a shared path
- `fix_patch` cwd is persisted and tied to the run id
- failed, pending, absent, or partial proposal state cannot produce usable MBE
  oracle evidence
- repeated `fix_patch` hashes across sibling candidates are explainable by
  identical applied proposal evidence, not shared mutable checkout state
