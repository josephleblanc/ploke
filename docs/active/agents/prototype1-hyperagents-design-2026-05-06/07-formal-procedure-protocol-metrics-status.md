# Status

The formal notation draft describes metrics as products of explicit procedures, executed by mechanized or adjudicative executors over admissible typed states, with separate roles for target metrics, evidential outputs, supporting metrics, recording, forwarding, graph composition, bounded inquiry, admissible actions, and valid terminal payloads (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:7`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:49`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:90`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:120`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:231`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:418`).

The real implementation is split. `crates/ploke-protocol` contains the typed procedure algebra and concrete tool-call protocol procedures. `crates/ploke-eval/src/protocol/mod.rs` is now a compatibility bridge that re-exports `ploke_protocol` and the eval aggregate loader (`crates/ploke-eval/src/protocol/mod.rs:1`). The files `crates/ploke-eval/src/protocol/components.rs` and `crates/ploke-eval/src/protocol/metrics.rs` are empty, and `crates/ploke-eval/src/protocol/procedures.rs` is an older sketch with local traits and `todo!()` bodies, not the active protocol implementation (`crates/ploke-eval/src/protocol/procedures.rs:1`, `crates/ploke-eval/src/protocol/procedures.rs:20`).

The current status is: the system has real carriers for procedure, executor, typed state, evidence policy, recording/forwarding disposition, binary sequence/fan-out/merge composition, executor provenance, persisted artifacts, concrete protocol metric values, and eval-side aggregate summaries. It does not yet have explicit first-class carriers for metric class membership, target/supporting/evidential role membership, arbitrary runtime DAGs with stable node ids, bounded inquiry states/actions, enforced admissible action sets, or full return-recovery loops.

# Implemented Formal Concepts

Procedure is real. `ploke_protocol::Procedure` has typed `Subject`, `Output`, `Artifact`, and `Error` associated types, and `run` returns a `ProcedureRun<Output, Artifact>` (`crates/ploke-protocol/src/procedure.rs:200`). A `Step<Spec, Exec>` is itself a procedure when the spec and executor satisfy the step traits (`crates/ploke-protocol/src/procedure.rs:215`). Named top-level procedures wrap nested artifacts in `ProcedureArtifact` (`crates/ploke-protocol/src/procedure.rs:495`, `crates/ploke-protocol/src/core.rs:114`).

Executor is real. `StepExecutor<Spec>` carries executor kind, label, provenance, and the async execution function (`crates/ploke-protocol/src/step.rs:29`). `ExecutorKind` distinguishes mechanized, LLM adjudicator, and human reviewer (`crates/ploke-protocol/src/core.rs:17`), but only mechanized and JSON LLM executors are implemented here. `MechanizedExecutor` executes `MechanizedSpec` and emits mechanized provenance (`crates/ploke-protocol/src/step.rs:48`, `crates/ploke-protocol/src/step.rs:63`). `JsonAdjudicator` implements `StepExecutor` for `JsonAdjudicationSpec`, parses structured JSON output, and records model/provider/raw response provenance (`crates/ploke-protocol/src/llm.rs:70`, `crates/ploke-protocol/src/llm.rs:93`, `crates/ploke-protocol/src/llm.rs:115`).

State is real but broad. `ProcedureState` is a marker over cloneable, serializable, sendable, debuggable types (`crates/ploke-protocol/src/core.rs:12`). `StepSpec` binds each step to typed input and output states (`crates/ploke-protocol/src/step.rs:6`). Concrete states include `ToolCallSequence`, `ToolCallNeighborhood`, `SequenceReviewContext`, `SegmentedToolCallSequence`, `LocalAnalysisContext`, `LocalAnalysisAssessment`, and `SegmentReviewSubject` (`crates/ploke-protocol/src/tool_calls/trace.rs:87`, `crates/ploke-protocol/src/tool_calls/segment.rs:52`, `crates/ploke-protocol/src/tool_calls/segment.rs:107`, `crates/ploke-protocol/src/tool_calls/review.rs:78`, `crates/ploke-protocol/src/tool_calls/review.rs:146`, `crates/ploke-protocol/src/tool_calls/review.rs:182`).

Evidential outputs are implemented as ordinary typed states and artifacts, not as explicit `U_x` role tags. Examples: `SequenceReviewContext` carries the original sequence plus mechanized `SequenceSignals` (`crates/ploke-protocol/src/tool_calls/segment.rs:52`); `SegmentationJudgment` carries the adjudicated segment proposals (`crates/ploke-protocol/src/tool_calls/segment.rs:69`); `LocalAnalysisContext` carries a bounded packet plus mechanized signals (`crates/ploke-protocol/src/tool_calls/review.rs:78`); branch assessments carry adjudicated usefulness, redundancy, and recoverability (`crates/ploke-protocol/src/tool_calls/review.rs:94`, `crates/ploke-protocol/src/tool_calls/review.rs:111`, `crates/ploke-protocol/src/tool_calls/review.rs:128`). Step artifacts preserve inputs, outputs, evidence policy, dispositions, and provenance at each execution boundary (`crates/ploke-protocol/src/core.rs:72`).

Supporting metrics exist as concrete fields and derived summaries, but not as first-class supporting-metric state membership. Mechanized signals and coverage are supporting evidence: `SequenceSignals` counts tool kinds, failures, repeated searches, directory pivots, and search terms (`crates/ploke-protocol/src/tool_calls/segment.rs:36`); `SegmentationCoverage` counts labeled, ambiguous, and uncovered calls/segments (`crates/ploke-protocol/src/tool_calls/segment.rs:97`); `LocalAnalysisSignals` captures local scope counts and candidate concerns (`crates/ploke-protocol/src/tool_calls/review.rs:55`). Eval aggregates preserve selected supporting fields as `ProtocolReviewSignals`, `ProtocolSegmentationCoverage`, and `ProtocolDerivedMetrics` (`crates/ploke-eval/src/protocol_aggregate.rs:51`, `crates/ploke-eval/src/protocol_aggregate.rs:91`, `crates/ploke-eval/src/protocol_aggregate.rs:193`).

Target metrics are represented by `Measurement` implementations and output value types, not by explicit `T_x` sets. `Measurement` names a metric with subject and value domains (`crates/ploke-protocol/src/core.rs:3`). Implemented protocol metrics are `tool_call_intent_segmentation`, `tool_call_review`, and `tool_call_segment_review` (`crates/ploke-protocol/src/tool_calls/segment.rs:120`, `crates/ploke-protocol/src/tool_calls/review.rs:158`, `crates/ploke-protocol/src/tool_calls/review.rs:170`). Their values are `SegmentedToolCallSequence` and `LocalAnalysisAssessment`.

Recording and forwarding are real at the artifact/state-disposition level. `StateDisposition` models `RecordOnly`, `ForwardOnly`, `RecordAndForward`, and `Ephemeral`, with helper predicates for recording and forwarding (`crates/ploke-protocol/src/core.rs:46`). `StepSpec::disposition` defaults outputs to `RecordAndForward` (`crates/ploke-protocol/src/step.rs:18`), and `Step::run` records input as `ForwardOnly` while preserving output disposition in `StepArtifact` (`crates/ploke-protocol/src/step.rs:120`). Eval persistence writes a top-level protocol artifact with schema version, procedure name, subject/run identity, model/provider, input, output, and nested artifact (`crates/ploke-eval/src/protocol_artifacts.rs:16`, `crates/ploke-eval/src/protocol_artifacts.rs:235`). The persistence layer stores the nested artifact; it does not enforce `StateDisposition` by selectively writing only states marked recordable.

Composed procedure graphs are partially real. `Sequence` enforces sequential typing through `Second: Procedure<Subject = First::Output>` (`crates/ploke-protocol/src/procedure.rs:297`). `FanOut` clones a common subject into two procedures and returns `ForkState<source, left, right>` while recording branch labels and artifacts (`crates/ploke-protocol/src/procedure.rs:349`, `crates/ploke-protocol/src/procedure.rs:365`, `crates/ploke-protocol/src/core.rs:92`). `Merge` runs a branch procedure, then a join procedure over the branch output, and keeps both branch and merge artifacts (`crates/ploke-protocol/src/procedure.rs:429`, `crates/ploke-protocol/src/procedure.rs:443`). This implements binary sequence/fork/merge composition, not the draft's more general runtime DAG with stable node ids (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:231`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:400`).

Bounded inquiry is mostly intended shape. The draft's `segment_tools` example describes inquiry states, inspect/return actions, budgets, failed return attempts, and explicit failure on retry exhaustion (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:511`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:545`, `docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:634`). The implementation instead runs a bounded, one-shot JSON adjudication over a pre-projected sequence packet and then normalizes the returned payload (`crates/ploke-protocol/src/tool_calls/segment.rs:181`, `crates/ploke-protocol/src/tool_calls/segment.rs:211`, `crates/ploke-protocol/src/tool_calls/segment.rs:318`). HTTP timeout, max attempts, and max tokens exist in `JsonLlmConfig` and CLI command configuration (`crates/ploke-protocol/src/llm.rs:24`, `crates/ploke-eval/src/cli.rs:6380`), but there is no typed `Q_x`, `A_x(q)`, action budget, no-repeat action set, or recovery state machine.

Admissible evidence is represented but weakly enforced. `EvidencePolicy` records allowed/forbidden evidence classes and hindsight/external-context flags (`crates/ploke-protocol/src/core.rs:33`). Concrete steps specify policies, for example sequence contextualization, intent segmentation, segment normalization, neighborhood contextualization, segment contextualization, and branch review policies (`crates/ploke-protocol/src/tool_calls/segment.rs:147`, `crates/ploke-protocol/src/tool_calls/segment.rs:193`, `crates/ploke-protocol/src/tool_calls/segment.rs:302`, `crates/ploke-protocol/src/tool_calls/review.rs:205`, `crates/ploke-protocol/src/tool_calls/review.rs:267`, `crates/ploke-protocol/src/tool_calls/review.rs:734`). These policies are recorded in artifacts and reflected in prompts; they are not capability-enforced action guards.

Return payload validity is partially real. LLM JSON is parsed into typed output states, with a small alias-normalization bridge for accepted JSON keys (`crates/ploke-protocol/src/llm.rs:142`). Intent segment normalization validates non-empty input, range bounds, overlap, labeled-segment labels, and ambiguous-segment label absence, then fails the procedure on invalid payload (`crates/ploke-protocol/src/tool_calls/segment.rs:262`, `crates/ploke-protocol/src/tool_calls/segment.rs:338`, `crates/ploke-protocol/src/tool_calls/segment.rs:357`). This is real payload validation, but it is not the draft's bounded invalid-return recovery loop (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:647`).

# Current Protocol Metrics

`tool_call_intent_segmentation` is a local sequence metric. Its subject is `ToolCallSequence`; its value is `SegmentedToolCallSequence` (`crates/ploke-protocol/src/tool_calls/segment.rs:120`). The procedure first computes `SequenceSignals`, forks the context into a preserved branch and an LLM segmentation branch, then merges by normalizing proposed segments (`crates/ploke-protocol/src/tool_calls/segment.rs:132`, `crates/ploke-protocol/src/tool_calls/segment.rs:178`, `crates/ploke-protocol/src/tool_calls/segment.rs:223`, `crates/ploke-protocol/src/tool_calls/segment.rs:259`, `crates/ploke-protocol/src/tool_calls/segment.rs:413`). The output records segment labels/status/confidence/rationale, turns, covered calls, coverage counts, uncovered spans, and overall rationale (`crates/ploke-protocol/src/tool_calls/segment.rs:75`, `crates/ploke-protocol/src/tool_calls/segment.rs:89`, `crates/ploke-protocol/src/tool_calls/segment.rs:97`, `crates/ploke-protocol/src/tool_calls/segment.rs:107`).

`tool_call_review` is a local call-neighborhood metric. Its subject is `ToolCallNeighborhood`; its value is `LocalAnalysisAssessment` (`crates/ploke-protocol/src/tool_calls/review.rs:158`). It contextualizes a focal call neighborhood, fans out three LLM branch judgments for usefulness, redundancy, and recoverability, then mechanized synthesis derives an overall verdict and minimum confidence (`crates/ploke-protocol/src/tool_calls/review.rs:190`, `crates/ploke-protocol/src/tool_calls/review.rs:321`, `crates/ploke-protocol/src/tool_calls/review.rs:353`, `crates/ploke-protocol/src/tool_calls/review.rs:385`, `crates/ploke-protocol/src/tool_calls/review.rs:417`, `crates/ploke-protocol/src/tool_calls/review.rs:462`, `crates/ploke-protocol/src/tool_calls/review.rs:890`). Output verdict classes include focused progress, useful exploration, recoverable detour, redundant thrash, mixed, and unclear (`crates/ploke-protocol/src/tool_calls/review.rs:135`).

`tool_call_segment_review` is the segment-level counterpart. Its subject is `SegmentReviewSubject`, which bundles subject id, original sequence, selected segment, and segmentation coverage (`crates/ploke-protocol/src/tool_calls/review.rs:170`, `crates/ploke-protocol/src/tool_calls/review.rs:182`). It uses the same three review branches and synthesis as call review, but contextualizes only calls inside the selected intent segment (`crates/ploke-protocol/src/tool_calls/review.rs:252`, `crates/ploke-protocol/src/tool_calls/review.rs:621`, `crates/ploke-protocol/src/tool_calls/review.rs:672`).

Recording happens through `write_protocol_artifact`, which serializes input, output, and the nested procedure artifact into a run-scoped JSON file after resolving and validating the run identity (`crates/ploke-eval/src/protocol_artifacts.rs:235`). The CLI paths persist all three main protocol procedures: call review (`crates/ploke-eval/src/cli.rs:5888`), segment review (`crates/ploke-eval/src/cli.rs:5948`), and intent segmentation (`crates/ploke-eval/src/cli.rs:6388`).

Summarization happens in `ProtocolAggregate`. The aggregate selects the latest segmentation anchor, normalizes call reviews and segment reviews, builds a segment crosswalk, computes missing review indices, counts artifacts, and derives counts for overall verdicts, confidence, crosswalk coverage, and average calls per anchor segment (`crates/ploke-eval/src/protocol_aggregate.rs:252`, `crates/ploke-eval/src/protocol_aggregate.rs:269`, `crates/ploke-eval/src/protocol_aggregate.rs:312`, `crates/ploke-eval/src/protocol_aggregate.rs:340`, `crates/ploke-eval/src/protocol_aggregate.rs:353`). It also rejects segment reviews whose packet no longer matches the selected segmentation anchor and reports them as skipped/mismatched evidence (`crates/ploke-eval/src/protocol_aggregate.rs:492`, `crates/ploke-eval/src/protocol_aggregate.rs:512`, `crates/ploke-eval/src/protocol_aggregate.rs:546`).

Eval-facing projection happens through `ProtocolAggregateReport`. It carries run/subject identity, provenance, coverage, segment rows, call issue rows, and notes (`crates/ploke-eval/src/protocol_report.rs:11`). `build_protocol_report` converts the aggregate into "Evidence reliability" with coverage, segment evidence status, call issues, duplicate artifact count, and anchor provenance (`crates/ploke-eval/src/cli.rs:8701`, `crates/ploke-eval/src/cli.rs:8814`). Campaign triage then folds reports across runs into protocol status, evidence totals, issue families, tool families, nearby segment labels/statuses, exemplars, and next-step suggestions (`crates/ploke-eval/src/cli.rs:7700`, `crates/ploke-eval/src/cli.rs:7722`, `crates/ploke-eval/src/cli.rs:7845`).

# Gaps

There is no explicit metric taxonomy for `O`, `N`, `C`, `D`, or `M_op`. The draft defines class membership in terms of reliable programmatic and adjudicative procedures (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:304`). Code has `Measurement` and concrete metric names, but no type or registry for obvious/non-obvious/conceptual classes, no `Op(x)`, and no reliability predicate `R(e, x)`.

Target metric, evidential output, and supporting metric are not encoded as separate roles. The output types make the intended role readable, and artifacts preserve intermediate states, but there is no durable role tag saying a state is `T_x`, `U_x`, `K_x`, or both. Consequently, eval aggregation must know procedure-specific JSON/output shapes and field meanings.

The global procedure graph is a nested compile-time composition, not a runtime DAG. `Sequence`, `FanOut`, and `Merge` preserve branch artifacts and branch names, which is important and real. But the draft's implementation note asks for a runtime graph with stable node ids, branch structure, and execution artifacts (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:405`). Current artifacts are nested Rust/JSON shapes with step ids and names, not a uniform graph table.

Bounded inquiry is absent as a typed state machine. The current implementation can bound the LLM request and validate the returned payload, but it cannot model "inspect item i, inspect item j, return payload" as admissible actions inside a procedure (`docs/workflow/evalnomicon/drafts/formal-procedure-notation.md:455`). There are no inquiry-state objects carrying inspected sets, remaining budgets, admissible next actions, return attempts, or explicit failure states.

Admissible evidence is mostly policy plus prompt, not enforcement. `EvidencePolicy` is a good carrier for the evidence contract, and it is stored in step artifacts. The executor still receives fully materialized input states; no guard proves that LLM prompts exclude forbidden evidence except by construction of the prompt/rendering code and review.

Return validity is fail-fast rather than recoverable. `NormalizeSegments` catches invalid segment proposals, and JSON deserialization catches malformed LLM output. That is useful for correctness, but the procedure terminates with an error instead of carrying a bounded recovery hint and retry count as the formal sketch proposes.

Eval aggregation is intentionally lossy. `ProtocolAggregate` normalizes artifacts into rows and counts, but loses nested branch artifact details, full LLM provenance, branch rationales beyond selected output fields, and step-level disposition semantics. `ProtocolAggregateReport` is even more projected: it is a human-facing reliability and issue report, not the source of protocol facts.

# Evaluation-Layer Implication

Before protocol metrics, the Evaluation layer was mostly endpoint/run operational selection. `OperationalRunMetrics` derives tool-call counts, failure counts, patch-apply state, repair-loop indicators, convergence, and oracle eligibility from run records (`crates/ploke-eval/src/operational_metrics.rs:36`, `crates/ploke-eval/src/operational_metrics.rs:71`). `evaluate_branch` compares baseline and treatment only on operational fields such as patch failures, retry counts, aborted repair loop, convergence, and oracle eligibility (`crates/ploke-eval/src/branch_evaluation.rs:25`). That is successor-selection useful, but it does not explain local process quality.

Protocol metrics add an Evaluation sublayer for process evidence. They do not merely count operations; they segment the trace into intent episodes, judge local usefulness/redundancy/recoverability, check coverage, reject stale segment reviews against the current anchor, and project cross-run issue families. This makes Evaluation less like a single scoreboard and more like an artifact-backed interpretation layer over trajectories.

The better high-level description is:

`ploke-eval` currently has an operational successor-selection layer plus a protocol-derived evidence layer. The operational layer decides whether a run looks better on coarse, programmatic outcome proxies. The protocol-derived layer explains how the run moved through tool-use state space by recording typed procedure artifacts, extracting local and segment-level adjudicated metrics, measuring coverage and artifact reliability, and folding those facts into run and campaign triage. It is not yet a fully formal procedure-graph evaluator, but it is more than operational metrics: it is the first implemented carrier for non-obvious, adjudicated process metrics inside Evaluation.
