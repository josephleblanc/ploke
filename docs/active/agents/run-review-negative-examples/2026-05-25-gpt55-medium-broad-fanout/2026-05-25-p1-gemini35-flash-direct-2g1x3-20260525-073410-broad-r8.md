## Verdict

r8 is a mechanically successful broad-headless-TUI attempt. It wrote the
request-declared submitted result, committed the candidate patch as
`fa223a9b380d46eaca3889afa2a6efbc465f3515`, and the main eval log records
that the broad harness admitted the submitted result.

The benchmark value is weaker than the mechanical outcome. The model claimed it
introduced per-server spawn locking in `ploke-ty-mcp`, but the committed patch
only adds and initializes a `spawn_locks` field. `rg` finds no reads or lock
acquisition, so that part of the claimed performance/concurrency change is
dead code. The real behavior change is removing redundant typed-client
`ensure_started` calls before `call_tool`. Final validation was focused on
`crates/ploke-ty-mcp`; it did not run the request-declared `ploke-eval`
validation contract.

## Patch Semantics

Actual committed changes:

- `manager.rs`: adds `spawn_locks:
  DashMap<ServerId, Arc<tokio::sync::Mutex<()>>>` and initializes it in
  `McpManager::from_config`.
- `context7.rs`: removes four direct `self.mgr.ensure_started(&self.id).await?`
  calls before `call_tool`.
- `git.rs`: removes six direct `self.mgr.ensure_started(&self.id).await?`
  calls before `call_tool`.

The final model message overstated the manager change. It claimed
`ensure_started`, `respawn_with_backoff`, and `start_autostart` were
synchronized by per-server locks. The committed diff does not do that:

```text
rg spawn_locks crates/ploke-ty-mcp/src/manager.rs ...
manager.rs:22: field declaration
manager.rs:31: initialization
```

So the lock field is present but unused. The client-side removals may reduce
redundant calls only if `McpManager::call_tool` already performs the required
startup check, which was the model's stated rationale and is consistent with
the local API shape it inspected.

## Trace Reconstruction

The model began with broad repository discovery, read `AGENTS.md`, checked
protected-core context, and localized on `crates/ploke-ty-mcp`. It ran focused
cargo before editing and had a green baseline for that crate.

The first semantic edit attempt failed because `apply_code_edit` used invalid
method canon paths. The second semantic edit staged the manager patch, but it
only resulted in adding the field and not the lock acquisition logic. Cargo
then caught a real compile error: `McpManager::from_config` did not initialize
`spawn_locks`. The model read the relevant initializer and repaired it with
`non_semantic_patch`.

After focused cargo passed again, the model removed redundant typed-client
startup checks in `Context7Client` and `GitClient`. Those two edits applied
cleanly. The final focused check/test both succeeded, and the terminal artifact
ended in `applied`.

The attempt contains `ScanForChange` and `IndexTarget { needs_parse: false }`
events after applied edits. I did not find evidence that a scan barrier,
stale-file hash, or `ContentMismatch` stopped r8. The main log shows
`index_workspace` starting for the r8 workspace, and it later records the
admission line, so indexing noise was not the terminal failure mode here.

## Positive Examples And Adjudication Candidates

Positive examples:

- The model used a model-visible cargo failure (`E0063`) to make a targeted
  repair instead of abandoning the attempt.
- It recovered from semantic-edit tool failures by switching to
  `non_semantic_patch`.
- It produced a committed, clean checkout and a submitted result that the broad
  harness admitted.
- It inspected protected-core guidance and kept edits outside `ploke-eval`.

Fields future LLM adjudication should extract:

- `submitted_result_exists`: true/false, with path.
- `admitted_by_harness`: true/false, with request id, changed path count, and
  log or typed admission source.
- `candidate_commit_sha`: commit id and dirty/clean checkout state.
- `changed_files`: result-reported paths and git-committed paths, compared.
- `cargo_contract_match`: whether recorded cargo commands match the request
  contract, not just whether some cargo command succeeded.
- `final_validation_strength`: focused crate, workspace, request-contract, or
  missing.
- `model_claim_vs_diff`: whether final prose claims are supported by the
  committed diff; r8 should be flagged for claiming spawn locking that was not
  implemented.
- `warnings_visible`: warning counts from final cargo summaries.
- `tool_failure_recovery`: whether failed edit or cargo output led to a
  targeted successful repair.
- `content_hash_or_scan_effect`: none observed for r8; preserve this field so
  stale-hash failures do not get conflated with successful attempts.

## What Is Working

- The complete-mode continuation hook can admit a broad-harness submitted
  result after a successful headless-TUI attempt.
- The result artifacts preserve enough edit, cargo, prompt, and admission
  evidence to reconstruct the attempt manually.
- The cargo tool exposed a compile error that directly guided a repair.
- The harness committed the admitted patch and left the workspace clean.

## What Is Not Working Yet

- Validation accounting still over-credits focused cargo success when the
  request contract asked for different checks.
- The final model summary can materially overstate what the diff implements.
- Warnings are counted but not made semantically prominent enough to prevent
  "cleanly" claims.
- The broad-harness child attempt still requires manual joins across submitted
  result, headless result, git state, and eval log to answer basic admission
  questions.

## Action Items

- Add a diff-supported-claim check for final model summaries, especially for

- Preserve r8 as a positive mechanical-admission example, but not as a strong
