## Failure Analysis

1. `terminal: applied` is overloaded. In these traces it means a proposal was applied to a candidate workspace. It does not mean the candidate passed validation, entered History, or became a valid successor. The r2 trace is the clearest example: it reports terminal `applied`, but every visible `cargo check -p ploke-tree` completion is `ok:false` / `compile_failed`.

2. The broad-harness request advertises evidence paths that are not all readable through the configured tool root. The first trace immediately tried to list the campaign `prototype1` directory and received an outside-root denial. That makes the model discover path policy through failures instead of through the prompt or typed tool contract.

3. Protected-path policy is reactive. In r2, the model tried to edit `crates/ploke-eval/src/cli/prototype1_state/history_preview.rs` and `crates/ploke-tree/Cargo.toml`, then got protected-path denials after it had already designed around those edits. The surface should predeclare or preflight protected paths before the model commits to a dependency or manifest-change plan.

4. Context acquisition dominated both attempts. The two traces used `48` combined `request_code_context` calls plus `48` combined `read_file` calls. That is a sign that the headless prompt supplied too little task-local context or too little high-signal target evidence for the model to act without reconstructing the repo.

5. Tool targeting errors were recoverable but noisy. The traces include `code_item_lookup` misses for `name_impl` and `LoopCommand`, an invalid `read_file` range, a `list_dir` call on a file path, and patch failures that required rereads. These are not the root cause, but they consumed turns and made the final evidence harder to interpret.

6. The r2 candidate quality was poor independent of tooling. It pursued a Rayon/dependency direction, hit a protected manifest boundary, then damaged `crates/ploke-tree/src/store/fs.rs` through repeated repair patches. The framework let the run end in an applied terminal state, but the candidate itself was not a coherent improvement.

7. The first candidate was mechanically healthier but weak as run evidence. It made a plausible micro-optimization in two `syn_parser` visitor files and reached an applied trace, but the artifacts do not show descendant performance evidence, History admission, evaluation output, or successor selection.

## Recommendations

1. Split trace terminal states. Keep `applied_to_workspace` separate from `validated`, `admitted_to_history`, and `selected_successor`.

2. Add a compact run-state summary artifact that joins: headless trace terminal, changed paths, validation command outcomes, scheduler status, node status, History presence, evaluation presence, and successor selection status.

3. Make protected paths and readable evidence roots first-class prompt/tool metadata. Do not make the model infer these boundaries through failed tool calls.

4. When a validation command fails after an applied patch, make that failure part of the candidate terminal state. A trace ending `applied` after repeated compile failures is misleading for run review.

5. Cap or summarize context-tool churn in trace review. `request_code_context` and `read_file` loops should produce a compact cluster summary before raw tool-event drilldown.

6. Treat closure metadata as protocol preparation evidence only unless run-state artifacts show the corresponding Parent/History/evaluation transition. Do not let closure completion imply a healthy Prototype 1 run.
