## Actionable Findings

1. Non-blocking eval issue, blocking edit-surface reliability issue:
   same-file edit refresh did not provide a clean recovery boundary after the
   first settled proposal in `util.rs`.

   Evidence: helper insertion applied at events 348/354/359. Follow-up
   `apply_code_edit` calls at events 373/376 and 420/425 failed with
   `Content changed ... Refresh or re-resolve`; `non_semantic_patch` calls at
   events 388/394, 404/409, 438/442, 455/458, and 478/483 failed with fuzzy
   same-file messages. The model eventually succeeded only by switching to a
   highly precise three-hunk patch at events 489/493/497.

   Action: add or strengthen a replay/regression for post-apply same-file
   follow-up edits so a model-visible refresh or re-resolve actually clears the
   stale semantic target, and protocol should classify repeated stale/fuzzy
   failures separately from generic transport failure.

2. Non-blocking eval issue, blocker for full protocol-complete claims:
   protocol lifecycle status is not procedure-complete.

   Evidence: `campaign.json` requires three procedures; protocol root contains
   only one segmentation artifact; `closure-state.json` reports all three
   procedures missing; run registration says protocol `completed`.

   Broken contract: protocol completion should mean all required procedures are
   present, or the lifecycle status should be partial/procedure-specific.

   Action: make the run registry and closure projection agree on required
   procedure completion, and avoid treating intent segmentation alone as a full
   protocol review.

3. Non-blocking eval issue: cargo validation records lose the requested package
   even when the provider used package-qualified calls.

   Evidence: response/event requests 84/738 and 85/747 include
   `package: "grep-printer"`. Event 742/750 results pass and stderr/stdout show
   `grep-printer`, but persisted results report `scope: workspace` and root
   manifest only. `validation-audit.json` has `package: null`.

   Action: persist both requested package and resolved package/manifest in the
   cargo result and validation audit. This would make final-response checking
   and later protocol review unambiguous.

4. Non-blocking information-quality issue: successful empty reads need a
   semantic warning when the requested range exists.

   Evidence: event 592 returned empty content for `standard.rs` lines
   3270-3300; direct checkout inspection shows those lines contain test code.

   Action: flag `ok:true` line-range reads with empty content when the file line
   count proves the range should exist, and have protocol count them as
   low-information successes.
