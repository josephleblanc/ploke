# Reviewer B: Transform/DB Type Graph Tightening Review

- Date: 2026-05-10
- Task title: Transform/DB relation emission and schema semantics review
- Task description: Review `typed_type_graph` transform emission, DB relation schemas, and parser `TypeRelation` / `type_use` / `type_contains` mapping for lax owner roles, ambiguous slot semantics, and broadened endpoint sets.
- Related planning files: `docs/active/agents/2026-05-10_tt-expr-core_type-resolution-handoff/README.md`, `docs/active/agents/2026-05-10_tt-expr-core_type-resolution-handoff/2026-05-10_current-type-resolution-state.md`, `docs/design/known_limitations/KL-008-typed-type-graph-constraint-surfaces.md`

## Findings

### High: `type_contains` emits qualified projection kinds that the DB API cannot decode

`transform_type_contains` now writes `QualifiedSelf` and `QualifiedTrait` containment rows for named projection nodes (`crates/ingest/ploke-transform/src/transform/type_graph.rs:298`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:300`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:303`). The DB-facing `TypeContainmentKind` enum and `from_str` decoder do not include either kind (`crates/ploke-db/src/type_graph.rs:98`, `crates/ploke-db/src/type_graph.rs:110`), and `Database::direct_type_contains` decodes every returned row through that enum (`crates/ploke-db/src/type_graph.rs:281`, `crates/ploke-db/src/type_graph.rs:296`).

Weakened invariant / caller-discipline risk: the transform and DB API no longer agree on the closed domain of `type_contains.kind`. Raw reachability queries still traverse these rows because they bind `kind` without decoding it (`crates/ploke-db/src/type_graph.rs:332`, `crates/ploke-db/src/type_graph.rs:335`), so corpus reachability can pass while the public structural API fails for the same rooted type. This makes qualifier containment a string-only side channel rather than a typed DB contract.

Recommended tightening tasks: add `QualifiedSelf` and `QualifiedTrait` to the DB-facing containment enum or introduce a separate typed qualifier edge if these are semantically not ordinary containment. Add a direct `direct_type_contains` contract over a qualified projection root, not only an end-to-end reachability contract. Prefer a shared transform-side `TypeContainmentKind` value or checked conversion instead of passing raw string literals from `insert_type_contains`.

### High: `slot_index` has role-dependent meanings that are not encoded in the relation

The persisted `type_use` row has only `owner_id`, `root_type_id`, `role`, and one `slot_index` integer (`crates/ingest/ploke-transform/src/schema/edges.rs:61`, `crates/ingest/ploke-transform/src/schema/edges.rs:65`). Transform emission assigns different coordinate systems to that same column. Function and method parameters use callable-local parameter index (`crates/ingest/ploke-transform/src/transform/type_graph.rs:33`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:166`). Field rows use the field node as `owner_id` but store the field's ordinal within its struct, enum variant, or union (`crates/ingest/ploke-transform/src/transform/type_graph.rs:52`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:67`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:92`). Generic owner bounds flatten all type-param bounds into one owner-local counter (`crates/ingest/ploke-transform/src/transform/type_graph.rs:179`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:186`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:194`). Where-clause subjects use predicate index, owner bounds use a flattened bound index, and generic-param-owned where bounds use only the bound index inside the current predicate (`crates/ingest/ploke-transform/src/transform/type_graph.rs:207`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:214`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:226`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:234`).

Weakened invariant / caller-discipline risk: `TypeUseRoot.slot_index` looks like one stable slot coordinate in the DB API (`crates/ploke-db/src/type_graph.rs:89`, `crates/ploke-db/src/type_graph.rs:93`), but callers must already know the role-specific hidden coordinate system to interpret it. For field-owned rows, the slot is not local to the owner at all. For `WhereGenericParamBound`, multiple predicates on the same direct type parameter can reuse `slot_index = 0`, losing predicate position. This is tolerable for coarse reachability, but it is too loose for exact slot reconstruction, duplicate detection, or future UI explanations.

Recommended tightening tasks: document and test a role-by-role slot coordinate contract before adding more roles. Better, replace the single optional integer with typed slot metadata such as `parameter_index`, `field_index`, `generic_param_index`, `predicate_index`, and `bound_index`, or use a compact `slot_path` that can represent nested coordinates. At minimum, make field-owned `FieldType` rows use `None` or a field-local coordinate and rely on existing field relations for parent field order.

### Medium: DB schemas erase parser-side endpoint families into broad UUID/string relations

Parser `TypeRelation` is explicitly typed as `OrdinaryTypeSourceId × OrdinaryTypeTargetId` or `TraitTypeSourceId × TraitTypeTargetId` (`crates/ingest/syn_parser/src/parser/relations.rs:19`, `crates/ingest/syn_parser/src/parser/relations.rs:26`, `crates/ingest/syn_parser/src/parser/relations.rs:38`, `crates/ingest/syn_parser/src/parser/relations.rs:44`). The type families are narrow: ordinary sources are only named type IDs (`crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:744`, `crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:760`), ordinary targets are structs/enums/unions/type aliases/type generic params (`crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:888`, `crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:894`), and trait targets are traits (`crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:905`, `crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:907`).

The DB projection stores all of this as `Uuid`, `String`, `String`, `String` (`crates/ingest/ploke-transform/src/schema/edges.rs:42`, `crates/ingest/ploke-transform/src/schema/edges.rs:50`). `TypeRelationSchema::insert_relation` records `source_kind` and `target_kind`, but queries join only on `source_id`, `target_id`, and `relation_kind` (`crates/ingest/ploke-transform/src/schema/edges.rs:241`, `crates/ingest/ploke-transform/src/schema/edges.rs:257`, `crates/ingest/ploke-transform/src/schema/edges.rs:260`, `crates/ingest/ploke-transform/src/schema/edges.rs:276`, `crates/ploke-db/src/type_graph.rs:343`, `crates/ploke-db/src/type_graph.rs:345`). `type_use` and `type_contains` have the same broad shape: arbitrary UUID endpoints plus string role/kind (`crates/ingest/ploke-transform/src/schema/edges.rs:61`, `crates/ingest/ploke-transform/src/schema/edges.rs:64`, `crates/ingest/ploke-transform/src/schema/edges.rs:114`, `crates/ingest/ploke-transform/src/schema/edges.rs:117`).

Weakened invariant / caller-discipline risk: fresh transform emission currently benefits from typed parser inputs, but the persisted schema and DB APIs do not reject invalid family crossings. Backup fixtures, manual inserts, future migrations, or new transform call sites could introduce `Trait` rows with non-trait targets, ordinary rows from non-named sources, or role/root combinations that no parser slot can produce. Because query code does not validate `source_kind` / `target_kind`, those invalid rows would become normal graphRAG candidates.

Recommended tightening tasks: add DB-level validation tests that intentionally insert bad rows and prove public queries reject or surface them as errors. Consider separate relation tables for ordinary and trait terminal relations, or add query predicates over `source_kind` and `target_kind` that enforce the parser family matrix. Move transform insertion from raw string/data-value functions toward typed wrappers that accept `TypeRelationKind`, `TypeUseRole`, and `TypeContainmentKind` values and validate endpoint families at the projection boundary.

### Medium: `AssociatedTypeBound` roots intentionally collapse associated-item ownership onto the containing trait

Trait associated type bounds are emitted as `type_use` roots owned by the containing trait (`crates/ingest/ploke-transform/src/transform/type_graph.rs:110`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:116`). The direct-root contract explicitly acknowledges that precise associated type item ownership is a future surface (`crates/ploke-db/tests/unit/type_graph_queries/direct_roots.rs:117`, `crates/ploke-db/tests/unit/type_graph_queries/direct_roots.rs:119`), and `KL-008` documents that associated type bounds are currently owned by the containing trait rather than a precise associated type item.

Weakened invariant / caller-discipline risk: this is a useful GraphRAG expedient, but it means the owner role is not the syntactic declaration owner. Multiple associated type bounds on the same trait are distinguished only by `slot_index`, and downstream callers cannot ask which associated type item introduced the bound without returning to parser-side metadata that is not represented as a DB owner. This will become more fragile when associated type defaults and impl associated type definitions are added.

Recommended tightening tasks: keep the current trait-owned row as an explicit derived/convenience surface if it is useful, but add precise associated-item nodes before broadening associated type/default support. Once precise owners exist, emit associated-type-owned roots and make any trait-owned aggregation obviously derived, either through a different role or a derivation marker.

## Correctly Constrained Parts

- Parser-side terminal relations are strongly constrained before transform persistence. `TypeRelation` does not accept broad `AnyNodeId` endpoints and keeps ordinary and trait resolution families separate (`crates/ingest/syn_parser/src/parser/relations.rs:19`, `crates/ingest/syn_parser/src/parser/relations.rs:33`).
- Ordinary type-use roots and terminal resolution sources are correctly separated. `OrdinaryTypeUseId` can represent composite roots, while `OrdinaryTypeSourceId` only admits named terminals after traversal (`crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:757`, `crates/ingest/syn_parser/src/parser/nodes/ids/internal/type_families.rs:804`).
- Composite where-clause subjects are not collapsed into direct generic-param-owned bounds. `direct_type_param_subject` rejects qualified, argument-bearing, and non-single-segment subjects (`crates/ingest/ploke-transform/src/transform/type_graph.rs:217`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:259`, `crates/ingest/ploke-transform/src/transform/type_graph.rs:265`), and there is an explicit DB test for the composite-subject exclusion (`crates/ploke-db/tests/unit/type_graph_queries/direct_roots.rs:187`, `crates/ploke-db/tests/unit/type_graph_queries/direct_roots.rs:218`).
- End-to-end transform ordering is sound for typed relation emission: `resolve_type_relations_after_tree` runs before the parsed graph is consumed, and only the resulting `TypeRelationReport` is persisted into `type_relation` rows (`crates/ingest/ploke-transform/src/transform/mod.rs:144`, `crates/ingest/ploke-transform/src/transform/mod.rs:181`, `crates/ingest/ploke-transform/src/transform/edges.rs:127`, `crates/ingest/ploke-transform/src/transform/edges.rs:133`).

## Recommended Tightening Sequence

1. Fix the `QualifiedSelf` / `QualifiedTrait` DB enum mismatch first because it is a concrete transform/API contract break, not only a modeling preference.
2. Freeze a role-by-role `type_use` slot semantics table and add DB tests for duplicate-sensitive shapes such as repeated where predicates on the same type parameter and field-owned rows.
3. Replace transform string literals with typed relation-kind/role wrappers, then make all string projection happen in one checked boundary.
4. Add DB invariant tests for invalid endpoint-family rows, either expecting rejection on insert or exclusion/error on public query.
5. Split precise associated-item ownership from containing-trait convenience reachability before implementing associated type defaults or impl associated type definitions.

No tests were run for this review. This report is based on static inspection of transform emission, schema definitions, DB query APIs, parser type-family definitions, and existing typed graph DB contracts.
