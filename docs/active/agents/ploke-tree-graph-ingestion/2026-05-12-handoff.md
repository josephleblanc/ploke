## Workflow: What Worked

- The `xtask orchestrate` board made the conveyor visible:
  records -> store -> graph build -> projection/review.
- Worker packets were useful for disjoint edit surfaces.
- Keeping one reviewer slot caught real issues:
  - uninitialized typed LLM payload index,
  - legacy `ToolErrorCode` spelling,
  - leftover retry-context JSON,
  - missing graph ingestion for attempt-scoped results,
  - label-only membership fallback in both playback and graph selection.
- Retainer agents were useful when scoped to one question:
  - confirmed `nodes/*/results/*.json` already uses `RunnerResultRecord`,
  - found exact `RuntimeId` assertion shape.
- The staggered pipeline was better than the earlier serial approach. Store work
  unlocked graph work while projection and records lanes continued independently.

## Workflow: What Did Not Work

- I initially duplicated the board with extra wrapper markdown reports. That
  added noise. The better rule is:
  - board for task state,
  - packet for worker instructions,
  - durable docs only for source-of-truth updates, substantive reviews, or
    compact handoff.
- The board stores report paths, and `xtask orchestrate complete --summary`
  now writes an inline completion summary to `.orchestrator/reports/` and
  attaches that generated report path to the task. Prefer this over creating
  one-off wrapper reports for ordinary completions.
- I used `complete` for review tasks but did not use `xtask orchestrate review`
  to mark the corresponding implementation tasks as reviewed. Future waves
  should use the review command so the board reflects acceptance cleanly.
- `block` has no obvious resolve/unblock path. Once a follow-up fixes a blocker,
  the board still shows stale blocked history.
- Worktree status is hard to reason about because another thread is modifying
  unrelated docs and `xtask` files at the same time. Future commits should stage
  only explicit graph-ingestion paths.
- `implementation-lanes.md` was not unused; it was superseded operationally by
  board tasks and packets once the conveyor became active. Keep it as the
  durable lane/ownership map and do not duplicate per-task state there.
