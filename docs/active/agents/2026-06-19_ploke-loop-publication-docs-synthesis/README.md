## Duplicate and conflicting narratives to reconcile before prose generation

1. Runtime-loop story duplicates across `src/prototype1/runtime-loop.md`, `drafts/runtime/loop.md`, active walkthrough, and live `cli_facing.rs`. Use `src/prototype1/runtime-loop.md` for short canonical terms, use the walkthrough for implementation details, and use `drafts/runtime/loop.md` only for motivation or older expanded explanations.
2. Parent/child channel story has an older file-protocol draft (`drafts/runtime/parent-child-channel.md`) and a pushed role-indexed channel implementation (`channel.rs`). Prefer `channel.rs` for current implementation claims; cite the draft as rationale/history.
3. Typestate story is explicitly unstable: `mod.rs`, `c2.rs`, and `c3.rs` say typed transitions are partially wired or not consumed by the live controller. Later prose must preserve the home-machine assumption and avoid declaring the VM typestate path complete.
4. Authority/Crown terminology appears in conceptual pages, formal proof targets, and code comments. Use `history-crown.md` and `runtime-authority.md` for public definitions, then check `authority.rs` and `history/**` for current enforcement details.
5. Evidence/persistence vs authority is a repeated potential confusion. `persistence-and-observability.md`, `history/stored/mod.rs`, `history/projection/mod.rs`, the June 6 persistence walkthrough, and the regression investigation all agree that logs/submitted results/projections are evidence, not promotion authority.
6. Candidate-generation/edit-surface model has multiple overlapping models by design debt. The June 9 proposal and migration log should be used to explain cleanup trajectory; do not flatten proposal, PR log, and live code into a single completed design.
7. General Ploke architecture docs (`PROPOSED_ARCH_V3.md`) are older and aspirational. They are good for motivation and top-level pipeline, but detailed pipeline docs must be refreshed against current crates before collaborator publication.
