Find the definition of a known code item. Better than grep.

Returns the code snippet of the item if it exists, and provides positive proof if the item does not exist.

Use this tool when you know the file path, item name, node kind, and crate-relative module path. `module_path` must start with `crate`, for example `crate` or `crate::module::submodule`; it is not the Cargo package name and it does not include the target item name.

If the module path is unknown, use `request_code_context`, `read_file`, or `list_dir` first. On success, the returned `canon_path` includes the item name and can be used as the `canon` value for `apply_code_edit`.

When call graph data is available, the result also includes node-scoped `call_context` and `proof_context` rows for callers, callees, callsites, and projected proof facts related to the resolved item. Exact lookups also include bounded `call_paths_from_owner`, `call_paths_to_target`, `call_impact`, `call_reach`, `call_reach_effects`, `external_summary_needs`, `runtime_dispatch_needs`, `local_bindings`, `local_binding_edges`, `returned_call_binding_flows`, `returned_future_flows`, and `returned_future_execution_flows` summaries.

Use `call_impact` to answer target-centered questions such as who calls this item, which callers eventually reach it, whether those callers are in test or non-test source, and what direct callsites resolve to it. The impact summary includes direct and eventual callers, `direct_call_sites` with `arg_count` and `generic_arg_count` metadata, `callsite_buckets` summarizing direct callsite kind and target relation counts, `test_callers`, `non_test_callers`, public direct callers under the stored visibility predicate, `source_files`, and `source_modules`. Node payloads include `module_path` so callers can group affected components without parsing `canon_path`.

Use `call_reach` to answer owner-centered questions such as what this item calls directly, which callees are reachable through resolved local call paths, what exact resolved `direct_call_sites` this owner makes with `arg_count` and `generic_arg_count` metadata, which direct `boundary_call_sites` cross displayed module paths, which transitive `boundary_edges` cross displayed module paths inside bounded resolved paths, which nonresolved `frontier_calls` are visible but fail closed, which `external_frontier_calls` represent dependency calls, which `unsupported_frontier_calls` represent visible resolver blockers, which `unresolved_frontier_calls` represent missing proof targets, and which `ambiguous_frontier_calls` preserve multiple possible targets without fabricating an edge. Its `source_files` and `source_modules` lists identify files and crate-relative modules to retrieve for explaining the call chain.

Use `call_reach_effects` to answer proof-annotated source/sink questions such as which reachable callsite has an admitted effect seed. Effect rows preserve the original targetless callsite payload, effect class, confidence, and blocker reasons; they do not turn external or unsupported frontier calls into local call edges. Pass `allowed_effects` to request `call_effect_policy_violations`, which reports reachable effect seeds whose effect class is outside that explicit allowlist. Use `external_summary_needs` to find reachable frontier callsites that still have an active `external_dependency_summary_missing` proof blocker before a trusted summary can be admitted. Use `runtime_dispatch_needs` to find reachable unsupported callsites with active `dynamic_dispatch_unbounded` proof blockers.

Use `local_bindings` and `local_binding_edges` to explain exact local callable proof such as initialized function-item bindings, aliases, constructed field projections, self-field assignment sources, and argument-to-parameter carrier edges. These rows explain already-admitted calls or visible fail-closed frontiers; they do not authorize additional traversal by themselves. Use `returned_call_binding_flows`, `returned_future_flows`, and `returned_future_execution_flows` for returned-callable and returned-future proof paths. Returned future rows are explanatory proof payloads and must not be treated as ordinary local call-path edges unless a separate resolved call edge is present.

Pro tip: use it with parallel tool calls to look up as many code items as you want.
