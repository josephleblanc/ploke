# 2606.00007 Deliberative Curation EigenTrust / Voting Weight Review

## Findings

### P1: Voting-weight inputs are not constrained to the paper's reputation/trust domains

The paper's effective weight formula combines a Beta reputation expectation and an EigenTrust component: `w_i = gamma * r_i + (1 - gamma) * t_i`, with `gamma` in `[0, 1]` and later caps `w_min <= w_i <= w_max` where `w_min > 0` (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:112-133`; `crates/ploke-selection-score/docs/text/formal-scoring.md:68-87`, `crates/ploke-selection-score/docs/text/formal-scoring.md:111-116`). The implementation only checks `reputation`, `trust`, and `gamma` for finiteness plus the gamma interval (`crates/ploke-selection-score/src/papers/deliberative.rs:23-31`). `bounded_voting_weight` only checks finite caps and `min_weight <= max_weight`, then clamps whatever scalar came back (`crates/ploke-selection-score/src/papers/deliberative.rs:40-51`).

That leaves invalid evidence representable and sometimes silently plausible: a caller can pass `reputation > 1`, negative trust, non-positive `w_min`, or an excessively large `w_max`, and the cap helper can hide the bad upstream state by returning an in-range value. The adjacent `beta_reputation` helper compounds this because it permits negative `alpha` or `beta` as long as `alpha + beta > 0`, so it can return a reputation outside `[0, 1]` (`crates/ploke-selection-score/src/papers/deliberative.rs:3-10`). This is an implementation limitation, not a paper limitation: the paper's Beta parameters are initialized at `(1, 1)` and updated/decayed as counts, so the intended domain is nonnegative evidence with a probability-like expectation (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:116-120`).

Tests cover gamma bounds and cap ordering, but not invalid reputation/trust values, non-positive caps, or invalid Beta parameters (`crates/ploke-selection-score/tests/deliberative.rs:3-22`). Before this mechanism feeds selection authority, the weight API should either take checked domain carriers or explicitly reject out-of-domain scalars before blending and clamping.

### P1: The current bounded weight helper does not encode Tier 0 fixed weight or role gates

The paper's voting-weight mechanism is coupled to a tier system: newcomers with `n(a) < n_thresh` have fixed `w_min` and no review or dispute privileges, Tier 1 gets review privileges, and Tier 2 can file disputes (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:130-140`). The Sybil argument also depends on new identities entering at `w_min`; the paper immediately caveats that per-identity bounds are weak when agent identity creation is cheap (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:339-346`).

`bounded_voting_weight` implements only scalar blending plus caps (`crates/ploke-selection-score/src/papers/deliberative.rs:40-51`). It has no interaction count, tier, role, or newcomer state. A caller can therefore assign a newcomer a blended weight above `w_min` if it supplies favorable reputation/trust values. This is acceptable only if the function is documented and used as a low-level blend/cap helper, not as the paper's full voting-weight mechanism. If promoted as "the" voting-weight mechanism, it breaks the cold-start and Sybil-bound assumptions.

### P2: `normalize_local_trust_row` can return a non-distribution for finite overflow

The paper requires each local trust row to be normalized as `C_ij = max(s_ij, 0) / sum_k max(s_ik, 0)`, with a uniform row when no positive interactions exist (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:120-129`; `crates/ploke-selection-score/docs/text/formal-scoring.md:77-83`). The helper rejects non-finite inputs and empty rows, clips negatives, and applies the uniform fallback for zero positive mass (`crates/ploke-selection-score/src/papers/deliberative.rs:60-70`).

The missing guard is `total.is_finite()`. With finite but very large positive scores, the sum can overflow to infinity; division by infinity then returns zeros, and the function returns `Some(vec![0.0, ...])` instead of a stochastic row. The shared `normalize_weights` helper explicitly treats non-finite sums as bad input and falls back to uniform (`crates/ploke-selection-score/src/common/probability.rs:8-15`), so this module already diverges from a safer local convention. The existing row tests cover clipping and the zero-positive fallback, but not finite overflow or a postcondition that returned rows sum to one (`crates/ploke-selection-score/tests/deliberative.rs:24-38`).

### P2: Fixed-iteration EigenTrust exposes no convergence status or residual

The paper defines global trust as the stationary distribution of the damped Markov chain, computed by power iteration, and its reputation-separation argument relies on convergence under explicit assumptions (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:128-129`, `crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:325-335`). `eigentrust_step` implements the transposed propagation and seed damping correctly for row-stochastic `C` (`crates/ploke-selection-score/src/papers/deliberative.rs:81-115`). `eigentrust_iterate`, however, returns only the vector after a caller-supplied fixed number of steps (`crates/ploke-selection-score/src/papers/deliberative.rs:124-138`).

The function docs honestly say it does not claim convergence (`crates/ploke-selection-score/src/papers/deliberative.rs:118-123`), but the return type is indistinguishable from a converged trust vector. That is risky if downstream code treats `t_i` as the paper's stationary EigenTrust component. The test suite asserts a two-step numeric example but does not check convergence tolerance, residual decrease, mass preservation over many iterations, or behavior on slow-mixing matrices (`crates/ploke-selection-score/tests/deliberative.rs:40-74`). A second-pass API should either keep this helper clearly named as fixed-step iteration or add a convergence-returning helper that reports iterations and residual.

### P3: Dense allocation shape is acceptable for paper fragments but should not become the production path by accident

`normalize_local_trust_row` allocates an intermediate clipped vector before producing the normalized row (`crates/ploke-selection-score/src/papers/deliberative.rs:65-70`). `eigentrust_step` allocates a fresh `next` vector per step, and `eigentrust_iterate` repeats that allocation once per iteration (`crates/ploke-selection-score/src/papers/deliberative.rs:103-115`, `crates/ploke-selection-score/src/papers/deliberative.rs:134-138`). The matrix representation is dense `Vec<Vec<f64>>` (`crates/ploke-selection-score/src/papers/deliberative.rs:81-85`).

For a source-backed scoring sketch this is fine. If the mechanism is later applied to many agents or repeatedly during candidate selection, the cost becomes `O(iterations * agents^2)` plus repeated allocation. The paper's own simulation used a closed population and fixed-interval EigenTrust computation rather than continuous recomputation (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:371-385`). The main agent should keep this implementation out of hot-path selection until either agent counts are small by construction or the code is reshaped around reusable buffers/sparse trust edges.

### P3: `Option` failure hides which invariant failed

All reviewed helpers collapse validation failure to `None` (`crates/ploke-selection-score/src/papers/deliberative.rs:4-18`, `crates/ploke-selection-score/src/papers/deliberative.rs:23-51`, `crates/ploke-selection-score/src/papers/deliberative.rs:60-138`). That keeps the fragment terse, but it makes malformed evidence hard to audit: a matrix shape error, non-stochastic row, invalid epsilon, zero iterations, bad caps, and invalid scalar domains all look identical. The crate already has a small `ScoreError` type for common scoring helpers (`crates/ploke-selection-score/src/common/error.rs:3-9`). This is not required for the paper sketch, but if the mechanism crosses into selector/reporting code, losing the invariant that failed will make run-review evidence weaker.

## Source-Paper Limitations, Not Rust Bugs

- The formal note already labels the exact fragments as source-visible but the whole governance protocol as not safely formalizable as one objective (`crates/ploke-selection-score/docs/text/formal-scoring.md:60-64`, `crates/ploke-selection-score/docs/text/formal-scoring.md:127-132`).
- Reputation separation is a stability argument under an honest weighted majority, not a guarantee of convergence from arbitrary initial conditions; the paper calls out the circularity, initial malicious advantage risk, and decay-rate sensitivity (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:325-335`).
- The simulation validates only a subset of mechanisms. Fast track, arbitration, subscription-based reviewer recruitment, and structured argumentation are not exercised; ground truth is synthetic (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:367-385`).
- Graduated sanctions and dispute limits were not exercised in simulation and remain empirically unvalidated in the agent context (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:591-595`, `crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:664-669`).
- Fundamental protocol limits remain outside these equations: prompt injection, model homogeneity, synthetic ground-truth assumptions, compute-proportional power, conduct gaming, and adaptive adversaries (`crates/ploke-selection-score/docs/text/2606.00007__deliberative-curation.txt:691-699`).

## Second-Pass Implementation Checklist

1. Add checked scalar/domain inputs before blending: probability-like reputation/trust values, `gamma` in `[0, 1]`, and `WeightBounds { min > 0, min <= max }`.
2. Make `beta_reputation` and `decayed_count` reject invalid count/decay domains rather than only checking finiteness and total positivity.
3. Either add a tier-aware weight API or rename/document `bounded_voting_weight` as only the low-level blend/cap helper, with Tier 0 and role gates handled elsewhere.
4. Harden `normalize_local_trust_row` against non-finite totals and add a postcondition test that every returned non-empty row sums to one within tolerance.
5. Add a convergence-oriented EigenTrust helper that returns `{ trust, iterations, residual }`, or keep fixed-step iteration separate and prevent callers from treating it as stationary trust.
6. Expand tests for invalid reputation/trust domains, invalid weight caps, Beta/decay preconditions, finite-overflow trust rows, long-iteration mass preservation, and slow-mixing convergence behavior.
7. If this mechanism enters a hot path, replace per-step allocation and dense matrix assumptions with an explicit small-agent limit or a sparse/reusable-buffer implementation.
